# Findings

## Initial State

- CubeMX generated code was just regenerated by the user.
- Earlier stable firmware used explicit clock/UART/camera repairs after CubeMX regeneration.
- The current project previously contained only the `waterlevel` X-CUBE-AI model in `H7serial.ioc`.
- Standalone analysis reports exist for `facedet` and `faceid`, but analysis output alone is not generated application code.

## Latest Model Analysis

- `facedet`: 2,560,772 B Flash; 3,317,208 B RAM; 3,276,864 B activations; 187,409,506 MACCs.
- `faceid`: 13,645,116 B Flash; 3,245,104 B RAM; 3,211,776 B activations; 447,532,768 MACCs.
- Both latest analysis logs end with `Analyze complete on AI model` and no capacity warning.
- `faceid` input is `1x3x112x112` float32 and output is a 512-value embedding.

## Current Project Configuration Check

- The latest CubeMX generation added `X-CUBE-AI/App/facedet*.c/h`, `X-CUBE-AI/App/faceid*.c/h`, `facedet_data.bin`, and `faceid_data.bin`.
- The current `H7serial.ioc` now contains three activation sizes and external SDRAM parameters, so the AI models are present in the generated project configuration.
- The generated project also added `Core/Src/fmc.c`, `Core/Src/quadspi.c`, and their headers.
- The working tree contains many generated-file modifications; only source files related to the requested regression will be changed manually.

## Regression Evidence

- Current `.ioc` values show `RCC.SYSCLKFreq_VALUE=153600000`, `RCC.HCLKFreq_Value=76800000`, and `RCC.FMCFreq_Value=76800000`, which do not match the previously validated 400 MHz / 200 MHz application configuration.
- Current `.ioc` sets `QUADSPI.ClockPrescaler=2` and `QUADSPI.SampleShifting=QSPI_SAMPLE_SHIFTING_HALFCYCLE`; these must be checked against the stable QSPI path.
- The generated output includes both face model weight binaries, but the application still needs explicit runtime model initialization and camera-1 capture coordination.

## Risks

- CubeMX may have reset UART baud, clock-tree selections, QSPI/SDRAM timing, or camera GPIO/DMAs.
- The two face models must not share overlapping QSPI weight locations if separate weight binaries are generated.
- The face models can share one SDRAM activation pool when run sequentially, but the pool must not overlap LCD or camera frame buffers.

## 2026-08-02 Implementation Findings

- `facedet` generated input is `1x3x320x320` float32 and has nine float outputs: three score heads followed by three box-delta heads and three landmark heads.
- `faceid` generated input is `1x3x112x112` float32 and output is a 512-float embedding.
- Generated activation configuration places model input/output inside the activation pool; the caller only needs to provide the pool base to `ai_*_create_and_init`.
- The generated QSPI weight address is compiled into `*_data.c`; changing only `.ioc` is insufficient after generation. Both source and `.ioc` must use distinct mapped addresses.
- The current QSPI diagnostics use indirect 1-line commands. Model execution additionally needs a QSPI memory-mapped read mode at `0x90000000`; a 1-1-1 fast-read mapping avoids depending on the Winbond QE bit.
- The current face diagnostic calls the water-level JPEG validation path. It must be replaced for the new face-AI mode with RGB888 decoding and `(pixel - 127.5f) / 128.0f` preprocessing.

## 2026-08-02 SDRAM and Model Direction

- The Apollo schematic identifies the external SDRAM as `W9825G6KH`; the exact speed suffix is not shown on the schematic.
- The STM32H743 FMC configuration uses a two-cycle divider, so the project target is `FMC kernel=200 MHz` and `SDCLK=100 MHz`.
- FMC and QUADSPI share PLL2. Both MSP clock configurations must use the same PLL2 output; QUADSPI is kept near 100 MHz with a prescaler of 2 when PLL2_R is 200 MHz.
- The new-core-board firmware was flashed and passed the complete memory diagnostics at 100 MHz: `kernel=200000000 sdclk=100000000`, `cache_rt ok`, and `SDRAM test ok ... size=32MB`.
- STMicroelectronics' STM32 AI Model Zoo provides `yunetn_320_qdq_int8.onnx` for face detection. It is UINT8 input, 320x320, and has small INT8 weights; the ST README lists deployment support for STM32N6, not STM32H7, so H7 compatibility still requires local ST Edge AI analysis.
- ST's model zoo does not contain an SFace model. OpenCV Zoo provides YuNet and SFace together, including `face_recognition_sface_2021dec_int8.onnx` and a block-quantized variant. This is a viable candidate pair for H743, but the application must implement five-landmark alignment and cosine/L2 matching itself.
- Local ST Edge AI 10.2 analysis for STM32H7 succeeded: YuNet uses 80,152 bytes of weights, 843,008 bytes of time-optimized activations, and 136.8M MAC; SFace uses 9,756,468 bytes of weights, 3,211,264 bytes of activations, and 614.8M MAC.
- YuNet generated I/O is INT8. Input quantization is scale 1, zero point -128, so RGB bytes map to `(int8_t)(pixel - 128)`. Its output tensors preserve candidate-major ordering from ONNX: `[1, anchors, 4]` boxes and `[1, anchors, 10]` landmarks.
- SFace generated I/O remains float32 despite internally quantized weights. It expects a five-landmark-aligned 112x112 RGB image in CHW order with raw 0..255 float samples.
- The first YuNet hardware run faulted with `CFSR=0x01000000` at model entry. SDRAM MPU region 1 was disabled, leaving `0xC0000000` as default Device memory; packed ST AI accesses require a Normal-memory MPU region and can fault on Device memory regardless of `UNALIGN_TRP`.
- After configuring SDRAM as 32 MB cacheable Normal memory, all 100 MHz memory tests still passed and YuNet completed in 848-851 ms. With a diagnostic-only synthetic five-point crop, SFace completed in 4,426 ms and produced a finite 128-D embedding; total decode + detect + align + recognize time was 5,328 ms.
- The measured YuNet + SFace latency is acceptable for one-shot pre-dispense authentication and is dramatically below the old 252-279 second pair. No model replacement is currently required.
- OpenCV documents a cosine threshold of `0.363` for SFace on LFW. The prototype's arbitrary `0.60` threshold was too strict for initial hardware validation and could reject repeated samples of the enrolled person; firmware now logs recognition status and measured cosine similarity on every completed SFace frame.
- The first post-fix live run confirmed repeated recognition of ID=1 (`status=0`, similarity `0.552` to `0.776`). The reported computer sound is not correlated with COM reconnects in the captured log: there are no serial errors or boot repetitions. The binary FAV1/JPEG stream contains arbitrary byte values, so any separate terminal configured to beep on received data/control characters should be closed or have receive-beep disabled; the WinForms viewer contains no beep or sound call.
## 2026-08-02 CubeMX model persistence

- The runtime and build files already used YuNet/SFace, but `H7serial.ioc` and `.mxproject` still identified the old `facedet/faceid` models.
- `H7serial.ioc` now records `waterlevel,yunet,sface` and uses project-local ONNX files under `models/face`, so future CubeMX sessions do not depend on temporary InsightFace files.
- The IOC also now records the validated 480 MHz SYSCLK, 240 MHz HCLK, 200 MHz PLL2_R kernel, 100 MHz SDRAM, 100 MHz QSPI and USART1 921600 settings.
- `tools/check_cubemx_regressions.ps1` is the required check after every CubeMX Generate Code. It is intentionally read-only and exits nonzero if generated settings or model build lists regress.
