# 养老智能饮水作品迁移至乐鑫 ESP32-P4 全流程

版本：V1.0  
日期：2026-07-17  
适用赛事：2026 年全国大学生物联网设计竞赛乐鑫科技赛道

## 1. 结论先行

本作品建议选用 **ESP32-P4-Function-EV-Board**，由 ESP32-P4 取代 STM32H743，承担摄像头采集、本地水位模型推理、传感器融合、泵控状态机、指纹识别、语音交互协调、数据记录和云端大模型交互。开发板上的 ESP32-C6 仅提供 Wi-Fi/BLE 连接，不作为业务主控。

最终参赛成品不应继续由 STM32H7 负责视觉和泵控、再把指定 ESP 芯片作为联网模块。赛题要求指定芯片作为“核心主控”，这种双主控分工存在明显合规风险。STM32H7 可以保留为迁移期间的行为基线和对照设备，但应从最终参赛架构中移除。

当前模型规模约 16.48 MMACC、172,390 个参数，ESP32-P4 的算力和 PSRAM 足以作为首选迁移平台。现有 ONNX 的核心算子也在 ESP-DL INT8 支持范围内，模型迁移可行，但 X-CUBE-AI 生成的 C 文件和量化参数不能直接搬到 ESP-IDF，必须重新生成 `.espdl` 模型并验证精度。

三款指定芯片的选型判断：

| 芯片 | 对本项目的适配度 | 判断 |
|---|---|---|
| ESP32-P4 | 高性能视觉、MIPI-CSI、最高 32 MB PSRAM、PIE AI 加速；开发板配 C6 联网 | 首选，最适合替代 H743 的视觉和控制职责 |
| ESP32-S3 | 集成 Wi-Fi/BLE、生态成熟、也有 AI 加速 | 可作备选，但摄像头、推理帧率、内存和多任务余量需先实测 |
| ESP32-C5 | 双频 Wi-Fi 6 和传感器连接突出，视觉算力不是主要优势 | 不建议承担本项目的 224x224 视觉主控 |

## 3. 当前 STM32H7 工程基线

当前工程的核心链路如下：

1. OV2640 通过 DCMI + DMA 输出 JPEG 图像。
2. STM32H7 软件解码 JPEG，生成灰度图并执行裁剪、遮罩、增强和量化预处理。
3. X-CUBE-AI 执行 INT8 模型，输出 5 类水位状态和连续水位回归值。
4. 业务状态机根据多帧识别结果控制泵，处理无杯、低水位、半杯、满杯和异常状态。
5. AS608 通过 UART 识别用户；外置语音模块通过 I2C 完成命令词识别与播报；OLED 显示状态。
6. STM32 通过 UART 向现有 ESP32 发送 `STM_FP:<id>` 和 `STM_DONE:<ml>`。当前接收初始化与命令解析为空，云端下行尚未形成完整闭环。
7. 当前饮水量由泵运行时间换算，并非实际流量或重量测量。

当前模型基线：

| 项目 | 数值 |
|---|---|
| 源模型 | `D:/v3_w05_origline_plus_newdata_qat_st_pure_int8.onnx` |
| 输入 | `1 x 1 x 224 x 224`，INT8 灰度 |
| 输出 | 5 类 logits + 1 个水位回归值 |
| 类别 | no_cup、low、half、full、abnormal |
| 参数量 | 172,390 |
| 计算量 | 16,479,543 MACC |
| 权重 | 约 182 KiB |
| 激活 RAM | 约 163.36 KiB |

迁移前必须冻结一版可复现的 STM32 固件、模型、阈值和测试数据，后续所有 P4 结果都与该版本比较。

## 4. 推荐目标架构

```text
MIPI-CSI 摄像头 ─┐
杯托称重 + HX711 ├─> ESP32-P4 ─> 本地融合与安全状态机 ─> 泵驱动/MOSFET
AS608 指纹模块 ──┤       │
语音模块/I2S音频 ─┤       ├─> 屏幕/OLED/语音播报
真实温度传感器 ──┘       │
                         └─> 板载 ESP32-C6 ─> Wi-Fi ─> 云端大模型
```

职责边界：

- P4：所有业务决策、视觉推理、传感器融合和安全控制。
- C6：网络连接，使用开发板官方网络方案向 P4 提供标准 ESP-IDF 网络能力。
- 云端大模型：解释饮水记录、生成提醒和自然语言建议，不直接绕过本地安全逻辑控制水泵。
- 本地安全层：无网时仍能完成放水、停水、异常保护和手动操作。

## 5. 硬件迁移

### 5.1 开发阶段硬件

优先申领赛事套件 2：ESP32-P4-Function-EV-Board。建议同时准备：

- 套件自带 MIPI-CSI 摄像头；
- 1 kg 称重传感器 + HX711；
- AS608 指纹模块；
- 现有 I2C 语音识别/播报模块；
- 现有 OLED，或直接使用套件屏幕；
- 真实温度传感器，仅在作品保留热水功能时安装；
- 泵、电源、MOSFET/驱动板、续流与浪涌抑制器件；
- 独立急停按键和硬件默认关断电路。

### 5.2 外设映射

| STM32H7 实现 | ESP32-P4 实现 | 迁移说明 |
|---|---|---|
| DCMI + OV2640 JPEG | MIPI-CSI + ESP-Video/板级 BSP | 首版建议使用套件摄像头，减少 DVP 接线风险 |
| X-CUBE-AI | ESP-DL + ESP-PPQ | 重新量化并导出 `.espdl` |
| HAL UART + AS608 | ESP-IDF UART 驱动 | 保留 AS608 协议层，替换收发与超时接口 |
| HAL I2C + 语音模块 | ESP-IDF I2C master | 首版保留原模块和词条，后续再切 ESP-SR |
| GPIO/软件 I2C OLED | I2C master 或 LVGL | 功能先迁移，界面升级后置 |
| GPIO/PWM 泵控 | LEDC/MCPWM + GPIO | 上电必须默认停泵，输出需经硬件驱动 |
| HAL Tick/Delay | `esp_timer`、FreeRTOS tick | 状态机不得使用长时间阻塞延时 |
| STM32->ESP32 UART | P4 内部事件总线 + C6 网络 | 删除旧的 `STM_FP`/`STM_DONE` 板间协议 |
| 泵时长估算水量 | 称重增量为主，时长估算为备 | 形成真实传感器融合并提高精度 |

### 5.3 摄像头选择风险

套件 MIPI 摄像头与现有 OV2640 的曝光、色彩、视角和畸变不同。即使网络结构不变，也可能出现明显域偏移。必须用新摄像头重新采集以下数据：

- 不同杯型、杯色、透明度和背景；
- 0%、低、半、满水位；
- 反光、气泡、遮挡、手部进入和杯体移位；
- 白天、暗光、侧光和室内灯频闪；
- 老年用户实际放杯速度和偏心放置。

若决定继续使用 OV2640，应先在 P4 上完成 DVP 采集最小验证，再确定引脚、驱动和帧格式。不要在模型迁移完成后才处理摄像头兼容问题。

## 7. 全流程实施步骤

### 阶段 0：冻结 STM32 基线

1. 记录当前可用固件哈希、编译日期和硬件接线。
2. 导出 200 至 500 张代表性图片及其 STM32 模型输出。
3. 保存每张图的预处理后 224x224 INT8 输入，避免只比较原图。
4. 记录泵控阈值、连续帧数、最长运行时间和故障语音。
5. 完成无杯、半杯、满杯、异常、移杯和摄像头故障测试视频。

验收：同一固件重复测试结果稳定，测试数据可脱离硬件重放。

### 阶段 1：建立 ESP-IDF 工程

使用赛事推荐 ESP-IDF v5.5.2：

```powershell
idf.py create-project elderly_water_esp32p4
cd elderly_water_esp32p4
idf.py set-target esp32p4
idf.py menuconfig
idf.py build
idf.py -p COMx flash monitor
```

工程要求：

- 开启 PSRAM，并先用板级示例验证内存；
- 使用固定分区表，预留双 OTA 分区和模型资源空间；
- 在 `idf_component.yml` 锁定已验证的 ESP-DL、视频、BSP 和网络组件版本；
- 不把 Wi-Fi 密码、API Key 或模型服务密钥写入 Git；
- 保存 `sdkconfig.defaults`，不要只保留本机生成的 `sdkconfig`。

验收：空工程可稳定启动，打印 P4、PSRAM、Flash、C6 网络和固件版本信息。

### 阶段 2：逐个打通外设

按风险顺序完成：

1. 泵控制 GPIO/PWM，上电和复位全过程保持关断；
2. 急停按键和最大运行时间保护；
3. AS608 UART 通信与指纹匹配；
4. 原 I2C 语音模块命令读取和播报；
5. OLED 或套件屏幕；
6. HX711 称重、去皮和标定；
7. 温度传感器；
8. MIPI 摄像头连续采集。

每个驱动均提供独立测试程序，不在泵控主流程中边联调边排查。

验收：每个外设连续运行 30 分钟无死锁；拔插或通信超时能恢复或进入安全状态。

### 阶段 3：迁移视觉预处理

1. 固定摄像头输出格式、分辨率、曝光和白平衡策略。
2. 在 P4 上复现现有灰度化、裁剪/填充、圆形区域限制和图像增强。
3. 对同一输入导出预处理结果，与 STM32 基线逐像素比较。
4. 把图像缓冲放入合适的 PSRAM/内部 RAM，避免频繁分配。
5. 使用双缓冲或队列解耦采集和推理，满队列时丢旧帧而不是阻塞安全任务。

验收：使用同一原始帧时，预处理数据差异可解释；连续采集无内存增长和撕裂帧。

### 阶段 4：迁移模型到 ESP-DL

1. 保存原始 ONNX、训练配置、类别顺序、输入归一化和校准数据。
2. 优先从训练框架重新导出适合 ESP-DL 的 ONNX；官方推荐 opset 18。现有 opset 13 可先做转换验证。
3. 审核算子。当前模型的 Conv、Add、Gemm、GlobalAveragePool、Flatten、Sigmoid、Squeeze 均有 ESP-DL INT8 支持。
4. 使用 ESP-PPQ 为 ESP32-P4 重新量化并导出 `.espdl`。不要直接使用 X-CUBE-AI 的 `waterlevel*.c`。
5. 用 200 至 500 张黄金图片比较 PC 原模型、STM32 输出和 P4 输出。
6. 将类别后处理、置信度、水位回归和阈值逻辑单独实现并测试。

建议验收门槛：

- 分类准确率相对浮点基线下降不超过 1 个百分点；
- 水位回归 MAE 增量不超过 0.02；
- 单帧端到端处理不超过 200 ms，持续达到至少 5 FPS；
- 连续推理 2 小时无内存泄漏、崩溃或输出漂移。

若量化精度不达标，依次处理：补充新摄像头校准集、采用 per-channel 量化、重新 QAT、再考虑调整网络结构。

### 阶段 5：迁移泵控状态机

保留现有核心状态：

- STANDBY；
- DECISION_WINDOW；
- DISPENSING_VOICE_WAIT；
- DISPENSING_AUTO_COLD；
- DISPENSING_VOICE；
- DISPENSING_MANUAL_COLD；
- DONE；
- FAULT。

使用 FreeRTOS 队列传递结构化事件，不让摄像、语音或云任务直接写泵 GPIO。只有 `dispense_control` 组件可以提交泵命令。

必须保留并加强的安全规则：

- 上电、复位、看门狗恢复、摄像头失效和传感器超时均默认停泵；
- 杯体移走立即停泵；
- abnormal 连续多帧才触发，计数只在实际出水状态生效；
- 达到目标重量或视觉水位即停泵；
- 视觉与称重明显冲突时停泵并提示重新放杯；
- 设置绝对最长出水时间，与模型结果无关；
- 云端、语音和 App 只能提出请求，不能绕过本地安全规则。

验收：对每个状态和转移建立表驱动测试；断网、断相机、断称重、移杯和模型异常均能停泵。

### 阶段 6：实现真正的传感器融合

推荐的最小融合算法：

```text
cup_present = 视觉类别为 low/half/full AND 杯重超过空杯阈值
dispensed_ml = (当前重量 - 去皮重量) / 水密度
level_valid = 视觉回归水位与重量换算水量在允许偏差内
user_context = AS608 用户 ID 对应的本地匿名档案

若 cup_present 为假、level_valid 连续异常或重量不再变化：立即停泵
```

融合不是把多个数值同时显示出来，而是这些数据必须共同影响判断。日志至少记录：时间、视觉类别/置信度/回归值、重量、温度、用户别名、目标水量、实际水量、状态和故障码。

养老场景可落地为：

- 指纹识别用户后加载其杯型去皮值和单次目标水量；
- 称重提供真实饮水量，视觉负责水位和溢出/杯体异常；
- 温度传感器限制热水输出并提示烫伤风险；
- 用户长时间未饮水时由云端模型生成简短提醒；
- 不把建议描述成诊断或治疗结论。

### 阶段 7：接入云端大模型

最稳妥的合规路径是“上行感知数据由大模型处理”，无需让云端直接控制水泵。

设备上传示例：

```json
{
  "device_id": "device-01",
  "user_alias": "user-03",
  "event": "drink_completed",
  "target_ml": 250,
  "actual_ml": 238,
  "water_temp_c": 42.3,
  "vision_level": 0.74,
  "local_time": "2026-07-17T09:30:00+08:00",
  "today_total_ml": 680,
  "abnormal_code": 0
}
```

模型返回必须采用固定 JSON Schema，例如：

```json
{
  "advice_text": "本次饮水量已记录，上午可再分两次少量补水。",
  "next_reminder_min": 90,
  "recommended_next_ml": 180
}
```

设备端校验：

- 限制文本长度和编码；
- `next_reminder_min` 与 `recommended_next_ml` 必须在本地允许范围内；
- JSON 解析失败时忽略下行并使用本地默认策略；
- 不上传原始图像、音频、指纹模板、姓名或联系方式；
- TLS 校验证书，密钥放安全配置或后端代理，不硬编码到公开仓库；
- 断网时将事件暂存 NVS，恢复后限速补传。

可使用赛事提供的边缘大模型网关、百度飞桨星河社区 API、硬件对话智能体，或赛事列出的其他云端模型。最终答辩必须展示真实请求、真实响应和设备行为，不能只展示 App 页面或预制文案。

### 阶段 8：系统联调和可靠性

建议任务优先级：安全控制最高，传感器采集其次，视觉推理再次，UI 和云端最低。云请求、TTS、屏幕动画和 OTA 不能阻塞泵控。

测试矩阵：

| 场景 | 预期结果 |
|---|---|
| 无杯启动 | 拒绝出水 |
| 放杯后语音选择半杯 | 语音完整播报，按目标重量/水位停泵 |
| 出水中移杯 | 立即停泵并记录故障 |
| 视觉异常 5 帧 | 停泵，播报异常，等待重新放杯 |
| 称重不变化但泵已启动 | 在超时内停泵，判定空转/堵塞 |
| 摄像头断开 | 停泵，进入 FAULT |
| Wi-Fi 断开 | 本地功能正常，记录排队 |
| 大模型超时/返回非法 JSON | 使用本地策略，不影响安全控制 |
| 设备复位 | 泵输出保持关闭 |
| 连续运行 8 小时 | 无泄漏、死锁、堆耗尽或异常复位 |

## 9. 参赛材料清单

### 9.1 必须能现场证明

- P4 是核心主控，工程 target 和板上芯片清晰可见；
- 至少一种真实传感器融合参与控制；
- 云端大模型真实在线调用；
- 上行非音视频感知数据或下行指令确实被设备处理；
- 无网络时本地安全功能仍可工作；
- 养老场景痛点与功能对应，不是通用饮水机换标题。

### 9.2 建议提交物

- 系统架构图、硬件连接图、BOM 和 PCB；
- ESP-IDF 源码、依赖锁定和一键构建说明；
- ONNX、`.espdl`、量化脚本、校准集说明和模型卡；
- 传感器标定、模型精度、推理性能和长稳测试报告；
- 云端接口说明、脱敏数据结构和异常处理；
- 3 至 5 分钟完整演示视频；
- 公开仓库时移除密钥、Wi-Fi 信息、指纹模板和用户隐私。

## 10. 主要风险与决策

| 风险 | 影响 | 处理 |
|---|---|---|
| 继续让 STM32 做核心控制 | 可能不符合指定主控要求 | 最终成品移除 STM32，P4 承担完整业务 |
| 更换摄像头导致模型失准 | 误停、误放或水位误判 | 新摄像头重新采集、量化和验证 |
| 直接复用 X-CUBE-AI 代码 | 无法编译或数值不一致 | 原始 ONNX -> ESP-PPQ -> `.espdl` |
| 仅按泵时长估算水量 | 传感器融合证据弱、精度低 | 增加称重或食品级流量传感器 |
| 大模型直接控制泵 | 延迟和错误输出带来安全风险 | 云端只给建议，请求经过本地规则和确认 |
| 热水温度只是预设显示 | 与真实工程不符 | 加真实温度传感器，否则删去测温宣称 |
| 把语音、视觉、云一次性全部重写 | 联调周期失控 | 首版保留 AS608 和原语音模块，分阶段替换 |
| API Key 放在固件或仓库 | 泄露和额度滥用 | 后端代理、安全存储、密钥轮换 |

## 11. 立即执行的第一批任务

1. 报名并优先申领 ESP32-P4-Function-EV-Board。
2. 将当前 ONNX、训练代码、校准数据、类别顺序和 500 张黄金样本集中归档。
3. 购买称重传感器 + HX711；确认是否真的保留热水功能，保留则加真实温度传感器。
4. 安装并固定 ESP-IDF v5.5.2，跑通官方 P4 摄像头和 C6 联网示例。
5. 建立新的 ESP-IDF 仓库，先迁移泵默认关断、急停和最长运行保护。
6. 同时启动新摄像头数据采集，避免模型迁移完成后才发现域偏移。
7. 选定一个云端大模型服务，先用 PC 验证结构化 JSON，再接入设备。
