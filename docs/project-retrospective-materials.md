# 饮水机工程问题与复盘素材台账

更新时间：2026-07-30

## 1. 文档目的

本文件保存比赛开发期间的关键事实、阶段版本、问题链路、验证依据和未完成事项。它不是最终复盘结论；凡是根因尚未通过对照实验闭环的内容，均明确标为“待确认”，避免后续把推测写成事实。

原始串口记录和最终引脚表保存在 `docs/retrospective-evidence/`，文件完整性信息见该目录的 `README.md`。

## 2. 系统目标与最终主流程

- 主控：STM32H743，承担水位视觉推理、状态机和水泵控制。
- 水位摄像头：OV2640，经 DCMI + DMA 采集 JPEG，软件解码后送入 X-CUBE-AI 模型。
- 出水入口：自动识别、语音半自动、机械/触摸按键三种方式。
- 身份识别：当前稳定版本使用指纹模块；下一阶段计划由第二颗 OV2640 和 H743 本地人脸识别替代。
- 通信：STM32 经 USART3 向 ESP32-C6 发送用户 ID 和本次出水量；ESP32 只负责通信/物联网，不承担主要视觉算力。
- 显示：当前主流程使用 OLED；后续更换 LCD 和触摸按键。
- 安全与展示：保留摄像头无效时的定时演示备用模式，但正常版本关闭 `PUMP_TIMED_DEMO_MODE`。

## 4. 关键问题记录

### 4.1 摄像头采集和 JPEG 解码

- 早期出现 JPEG 解码失败、画面间歇性失败、AI 可视化模式卡顿以及 FPS 从约 4 降至约 2 的现象。
- 已验证过 OV2640 探测成功、JPEG 格式设置、图像尺寸设置、AI 初始化和 DCMI 数据链路。
- CubeMX 重新生成代码曾重置摄像头相关 GPIO、时钟树和串口配置，因此每次重新生成后必须对照稳定提交检查 `.ioc`、时钟、DCMI、DMA、JPEG 和 UART。
- 模型稳定性明显受自动曝光、环境遮挡恢复、杯体位置和出水水流影响。仅提高单帧阈值不能解决域偏移，必须结合曝光锁定/稳定等待、多帧判决和现场验证集。
- 复盘重点：把“摄像头采集失败”“JPEG 解码失败”“图像有效但模型误判”分成三类指标，避免用一个 `cls` 日志混在一起判断。

### 4.2 水位模型和半杯/满杯阈值

- 半杯曾出现两种相反问题：低水位很快被判为半杯而提前停水，以及直接从低水位跳到满杯、很少稳定出现半杯。
- 已采用“视觉主判 + 时间上限兜底”的半杯策略，并基于实际串口记录反复调整停水阈值。
- 满杯流程曾稳定完成，后续阈值修改又引入“刚放一会水就异常停水”和“满杯无法正常停水”的回归。修复时必须以历史成功日志为基线，不能只围绕失败日志继续叠加阈值。
- 第二次放入空杯后长期 `cls=2` 的现象没有证据表明软件写死第二次流程，更可能与杯子位置、残留水滴、曝光和场景变化有关；该结论仍需受控 A/B 测试。
- 400 ml 满杯标定和多次完整出水日志已归档，可用于赛后重新计算流量曲线，而不是只保留最终常数。

### 4.3 出水状态机和异常保护

- 曾出现“水杯已识别/水位播报尚未结束就立即启动或被异常停水打断”，说明语音播放、命令窗口和异常检测之间存在时序耦合。
- 曾出现出水结束后持续显示异常，表明完成态、杯子移走判定和异常帧计数需要在会话边界正确清零。
- 水流过快、细出水口导致飞溅和气泡，属于机械流体问题，同时会反馈影响视觉识别；不能只通过模型阈值补偿。
- 备用演示模式用于现场摄像头异常时按定时方式展示三种入口，不应替代正常视觉闭环。正常工作时 `PUMP_TIMED_DEMO_MODE=0U`。

### 4.4 水泵与硬件驱动

- 遇到过 MOS 管控制端有电压但水泵不转，排查时需要分别测量栅极、漏极、源极、电源压降和泵两端带载电压，不能只看控制电压。
- 单独测试阶段曾使用水泵常开模式；该模式只能用于短时硬件排查，不能保留在正式固件。
- 最终引脚方案预留 PWM 水泵和补光灯；水泵计划迁移到 PI0。最终引脚表已归档。

### 4.5 指纹模块

- 指纹模块出现过 `connect fail code=0xFF`、待机不识别和进入窗口期后才显示 ID 等问题。
- 后续方案是在 standby 常驻轮询并锁存最近一次 ID，使机械、自动和语音入口共享身份结果。
- 锁存 ID 不应改变 ESP32 上报语义：一次出水会话只上报该会话绑定的 ID 和最终出水量。
- 下一阶段以第二摄像头人脸识别替代指纹，但在 H743 人脸链路完整验证前保留稳定指纹版本作为回退。

### 4.6 STM32 与 ESP32 通信

- PB10/PB11 对应 USART3 TX/RX；曾通过固定轮询发送 `STM_FP:1` 和 `STM_DONE:320` 检查链路。
- STM32 日志中 `HAL_OK` 或 `status=0` 只能证明数据交给 UART 外设，不等价于 ESP32 已解析、更不等价于云端数据已经更新。
- 已建立 `[ESP32_TX]`、`STM_FP:<id>`、`STM_DONE:<ml>` 日志。完整闭环需要同时保存 ESP32 接收日志和云端更新结果。
- 复盘重点：通信验收应分为 STM32 发送、物理波形、ESP32 接收、协议解析、云端提交五层。

### 4.7 水箱水位传感器

- PB5 水位传感器最初被加入控制保护，随后需求明确修正为“只在 OLED 显示，不参与泵控、异常、语音或 ESP32 上报”。
- 因硬件状态不稳定，当前阶段又临时改为一直正常。
- 该传感器和视觉杯内水位不是同一个概念，文档和变量命名应始终区分 tank level 与 cup water level。

### 4.8 双摄像头

- 两颗相同 OV2640 的数据、时钟、SCCB 和 RESET 信号并联，PWDN 分别控制，H743 分时只唤醒一颗。
- `APP_MODE_DUAL_CAMERA_DIAG` 已连续交替探测两颗相机并捕获有效 JPEG。
- `APP_MODE_FACE_DIAG` 已稳定选择 cam=1，JPEG 有效且实际约 15 FPS；先前显示 1.8 FPS 是统计口径问题，已由 `5cac4ea` 修复。
- 分时切换时必须停止 DCMI/DMA、切换 PWDN、等待传感器稳定、重新应用对应寄存器配置，再开始采集；严禁两颗摄像头同时驱动并联数据总线。

### 4.9 人脸识别和内存预算

- 主要算力必须在 STM32H743，ESP32-C6 仅负责通信，因此放弃用 ESP32-S3 独立完成人脸识别的方案。
- `buffalo_sc` 对 H743 过大，不能把完整桌面/移动端模型包直接等同于可部署的 X-CUBE-AI 单网络。
- 小型 MobileNet/MobileFaceNet 路线仍需要人脸检测、对齐、特征提取、注册模板和相似度判决，不只是导入一个分类 ONNX。
- 当前 LCD 编译产物的大部分内部 Flash 被背景图占用；图像资源迁移到 QSPI 可回收约 906 KiB。
- 人脸识别与水位识别不需要同时运行，计划分时复用外部 SDRAM 激活区；模型权重放 QSPI，内部 SRAM 保留实时控制和 DMA 必需区。

### 4.10 LCD 和最终引脚迁移

- LCD 与触摸在综合实验中识别为 `LCD ID:5510`、`CTP ID:911`，基本显示和触摸可用。
- LCD 驱动直接写 LCD GRAM，不要求完整帧缓冲常驻内部 SRAM；大图资源应迁移到 QSPI。
- 冷水机械按键将移除，后续使用 LCD 触摸按钮。
- 最终引脚表是唯一有效来源；旧版临时引脚分配不得继续引用。

### 4.11 QSPI NOR Flash

- 外部 QSPI NOR 的 JEDEC ID 为 `EF4019`，对应 Winbond W25Q256 一类 256 Mbit/32 MB 器件，基础命令通信成功。
- 状态寄存器记录为 `sr1=00 sr2=02 sr3=60`。
- `SFDP=FFFFFFFF` 不能单独判定芯片损坏；旧官方例程可能让器件停留在 QPI 模式，MCU 复位后单线命令会失效，需断电或显式退出 QPI。
- QSPI 与 NAND 是独立器件；拆除 NAND 不影响 QSPI。

### 4.12 SDRAM、FMC_D6 与 NAND

- SDRAM：U3 W9825G6KH；NAND：U4 MT29F4G08。
- 原理图确认 `FMC_D6` 同时连接 MCU `PE9`、SDRAM U3 `DQ6 pin 11`、NAND U4 `I/O6 pin 43` 和外部连接器。
- SDRAM 物理读回反复出现固定 D6 错误，例如 `expected=0x851ABDC1`、`got=0x855ABDC1`、`diff=0x00400000`。
- 错误在 100/80/50 MHz、ReadPipe 0/1/2、LCD 接入/拔除、不同 MPU/cache 配置下均复现。
- PE9 到 SDRAM DQ6 连通；NAND 片选 PG9/NCE3 读到高电平并主动拉高后错误仍存在，因此已排除正常片选误动作，但尚未排除 NAND I/O6 损坏后的漏电或钳位。
- 正点原子实验 14 的可见数组打印受缓存影响，不能作为物理 SDRAM 完全正常的充分证据。关闭 D-cache 后的 CPU 探针仍读到 D6 固定位异常。
- 综合实验 65 确实使用 SDRAM 作为 LTDC 帧缓冲和外部内存池；LCD 能运行说明 SDRAM 不是“完全不可访问”，但不能否定 CPU 物理往返测试中的可重复单比特错误。
- 综合实验 65 同时出现 NAND ECC 多比特错误和 `NAND Flash Fat Error`，增加了 NAND 器件或共享总线异常的嫌疑，但尚不能证明 NAND 是 SDRAM D6 根因。
- 下一步受控实验：先抬起 U4 pin 43，或在专业返修条件下拆除整个 NAND，然后重跑同一份 50 MHz SDRAM 诊断。只有隔离前后唯一变量是 NAND I/O6 时，结果才可用于判定根因。

## 7. 赛后复盘建议结构

1. 目标和约束：ST 赛道、H743 主算力、时间限制和展示要求。
2. 系统演进：单摄水位识别到稳定出水，再到 ESP32、备用模式、双摄和人脸识别。
3. 最困难问题：视觉域偏移、状态机时序、FMC 共享总线和 CubeMX 再生成回归。
4. 有效方法：建立稳定 Git 基线、保留原始串口、单变量实验、区分软件可见结果与物理往返证据。
5. 无效方法：只改阈值、重复试时钟参数、把 UART 发送成功当成端到端成功、把缓存命中当成 SDRAM 正常。
6. 最终改进：自动化硬件回归、版本/固件哈希记录、数据集覆盖现场光照和机械水流、模块化引脚配置。
